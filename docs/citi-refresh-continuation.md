# Citi：默认全选与逐条继续

> 更新：Chase 从 1.6.0 起支持点击添加及逐条状态回读，见 [当前接口说明](chase-api-contract.md)。下文关于 Chase 只读的描述为该次历史发布状态。
## 当前操作

首次点击 **Load cards & offers** 读取全部卡片和优惠，默认全选，不自动添加。页面加载和缓存恢复本身不发请求。

- **Add saved offers (N)**：先核对当前登录卡片归属，再处理已选卡中缓存为 `AVAILABLE` 的优惠。正常缓存不逐卡刷新；上次失败、扫描不完整或卡片请求标识变化时，在这次点击内核验所选卡的当前优惠，再处理缓存中原先可用且当前仍可用的项目。已添加、未确认和冲突记录都跳过，搜索只影响展示。
- **Refresh & add offers**：刷新所有当前卡的优惠，再添加选中卡的可用优惠。新发现的卡默认勾选，已有手动取消的选择保留；未选卡只读取优惠。
- **Stop**：等待当前请求返回并保存结果，然后停止发出后续请求。添加阶段停止后可点 Add saved offers 继续剩余优惠；未确认项仍跳过。刷新中止也保留此前完整缓存，下次点击可核验后继续。

## 单条问题与整批失败

Citi 返回 HTTP 200 JSON，但没有明确登记成功时，记录该条 `UNCONFIRMED`，保存进度并继续下一条，不把它计入已添加，也不重发。已有未确认或冲突条目不再禁用整批缓存添加。UI 显示跳过原因和刷新核验入口；结束统计分别展示明确成功数量和未确认数量。

这直接覆盖一条未确认导致其余 225 条无法添加的情况。显式刷新后，如果银行已将该条标为已添加，就继续跳过；只有重新读取为可用时，才会进入这次用户主动刷新并添加的队列。

HTTP 错误、429、网络失败、超时、非 JSON、登录不匹配、存储失败和扫描未完成仍停止。429 按银行要求冷却；失败标记会保存，但不再永久禁用缓存按钮；下次明确点击先核验当前状态，不自动重发未知写入。仍然串行、按响应完成计时、没有自动重试或自动恢复。当前调速参数见 [自动调速](adaptive-pacing.md)。

## 重开页面与卡片标识

1.5.3 在实际页面上出现过：五张卡全选，状态报卡片不匹配，随后优惠变成 0。旧代码在检查匹配前就替换卡片并删除旧 ID 对应的优惠；完整刷新也错误地让旧选择否决当前列表。

修复后完整刷新先读取当前全部卡片和优惠，成功后一次性替换缓存，再处理当前选择，不要求旧请求标识仍有效。失败和 Stop 都不会提交一半的新结果。

缓存添加先核对卡片；ID 改变时，只用双方唯一且含四位尾号的完整显示名称关联选择。名称关联本身不授权缓存写入：必须先读取当前卡的优惠，并限定为原缓存中的可用 Offer ID，不添加此次核验才发现的新优惠。未确认、已确认和已消失的缓存优惠不会重发。名称模糊、重复或真正不匹配时保留缓存并停止，用户可用完整刷新建立当前卡片列表。

现场已确认旧版误清缓存和灰按钮；现有 HAR 只有一次完整卡片列表，不能单凭它认定 Citi 标识一定随登录轮换。标识变化、登录不匹配和缓存恢复均用合成数据验证。

## 选择和旧数据迁移

Citi 和 Chase 首次默认选中全部卡，新发现卡片默认勾选。手动取消，包括全部取消，跨刷新和重新检测保留。Chase 仍只读取优惠，不新增未验证的登记接口。

通用 workspace 升到 schema 3，保留原存储键、卡片、优惠、时间戳和显示偏好。schema 1/2 没有标记区分初始空选择与用户主动全不选，因此旧版空选择一次性迁移成全选；已有非空选择按原样保留。schema 3 明确保存初始化标记，之后的主动全不选不会再被重新勾选。读取只在内存迁移，下次明确保存才写入新格式。Amex 独立优惠快照仍为 schema 2。
